Runtime

Harnesses become managed services

The runtime turns command-line agents into tenant-scoped services that any caller can invoke and any operator can govern.

Harness profiles are data

A profile names the executable, ordered argument templates with conditions, environment, files to write, how the prompt and system prompt are delivered, the MCP configuration format, and the parser that turns output into events. Clone a built-in and edit it without a release.

Harness profiles

Every prompt is a template

System prompts, task wrappers, delegation and fan-out instructions, MCP tool and A2A skill descriptions, and harness config files are versioned templates with a live preview. Every run records the versions it rendered.

Prompt templates

Revisions and deployments

Agents keep immutable revisions. A deployment binds a revision, or follows the latest published one, to a harness, prompts, MCP servers, secrets, a workspace, an environment, placement, and limits. Weights split traffic.

Revisions and environments

Four ways in

REST with server-sent events, an MCP server, and an A2A gateway with one agent card per agent share tenants, credentials, and RBAC. Apps add the app gateway, which accepts only app sessions.

REST · MCP · A2A

Agents that call agents

Runs get a short-lived, lease-fenced run token. With delegation on, an agent invokes the agents its allow list names, one at a time or several at once, within depth limits, never with more permission than the person who started the chain.

Fan-out and gather

Files that outlive a turn

A conversation file space is shared by every turn and every delegated run. It syncs into the workspace at run start and back at run end, with per-path versions. A stale write is kept under a conflict name rather than lost.

File spaces

Agent assets

Versioned skills, reference files, document templates, and system prompts, pinned by revisions and placed where each harness expects them. Claude Code skills land in .claude/skills/. Workers verify every file's SHA-256.

Agent assets

Capability catalog

One descriptor per Garrison agent, MCP tool, or host program, with input and output schemas and cost and latency hints from real runs. Orchestrators read it through MCP tools to decide what to call.

Capability catalog

Approvals, pipelines, triggers

Tool-call approvals with allow, deny, and ask rules and a deny-by-default timeout. Pipelines with review gates between stages. Cron and HMAC-signed webhook triggers, and signed outbound notifications.

Scaling

Scale your agents as big as you want

Control-plane replicas and workers scale independently. Workers pull work over outbound connections and never touch the database.

Workers pull

A worker runs up to MaxConcurrentRuns harnesses at once (4 by default). To scale out, add replicas: a new worker registers, reports its harnesses and labels, and starts long-polling within seconds. On SIGTERM it stops leasing and finishes its runs for up to 900 seconds.

Any replica serves any client

Claims are a single compare-and-set update with a fencing epoch, so two workers never own a run. Events stream from the database, so an SSE stream, MCP session, or WebSocket can be served by any replica. Maintenance is leader-elected through a database lease. More than one replica needs PostgreSQL.

Delegation that cannot deadlock

Waiting parents lend reserve slots to their children, children are claimed ahead of new top-level work, and a wait that could never be served fails fast with DelegationCapacityExhausted. With durable continuation, a parent checkpoints and frees its slot while it waits.

Fan-out and gather

One call starts up to Delegation.MaxFanOutWidth members (default 8, up to 64), each checked against the allow list first. Gather returns partial results under All, Any, or Quorum joins, and groups end on timeout, cost or token budget, or cancellation.

Kubernetes

The production overlay runs three control-plane replicas with an HPA from 2 to 10, disruption budgets, and four workers. The KubernetesJob executor gives every run its own pod with an egress allowlist, and worker pools separate kinds of work.

Garrison Agent Studio

Design and deploy agents seamlessly

The studio is where agents and apps get designed before anything changes in live configuration. A person, the agent architect, or both edit a draft; a person approves applying it.

  1. Draft

    A draft is a set of manifest documents: agents, deployments, prompt templates, assets, an app and its edges. Start empty or from an existing app. Every change names the draft version it read, so two editors never overwrite each other silently (DraftVersionConflict).

  2. Diff and validate

    The studio shows each item as Create, Update with field changes, Delete, or Unchanged against live configuration, and validates the draft with a manifest dry run. Drafts never hold secrets; they refer to them by name.

  3. Try it in the playground

    Playground runs try an agent's draft revision on a temporary deployment in the reserved draft environment. They keep conversations and file spaces, but no app can reach them. Compile preview shows the exact command line, asset paths, and file space mount for a revision and environment.

  4. Approve and apply

    Requesting an apply creates a DraftApply approval. A person with permission to apply manifests decides it; the draft is re-validated at decision time, applied in one transaction, revisions publish, and the app deploys to dev.

  5. Promote and roll back

    Promotion moves a published revision, or a whole app, from dev to staging to prod in one transaction, under one promotion record. Rolling back restores every pin together.

Agent Studio · Revisions and promotion

The agent architect

A protected agent seeded in every tenant. Give it a deployment on the harness and model you want, describe the app, and it writes the draft through studio MCP tools. It can change the draft as often as you like; it cannot make it live.

The agent architect

Architect prompts

Two built-in prompts ship: builtin/agent-architect and the step-by-step builtin/agent-architect-guided. Clone one, edit it, and select it for a deployment; an unpinned selection applies on the architect's next turn.

Architect prompts

The Drafts grant

Architect runs edit only the drafts of the person talking to them, within that person's permissions. They can never apply a draft, decide an approval, delete live resources, or read secret values.

Delegated management

Canvas

The draft's apps as boxes and arrows, with solid arrows for calls that may fan out and dashed ones for calls made one at a time. Property and runtime panels edit agents and per-environment deployments.

Canvas

Live sync

The canvas follows the draft's studio-draft channel. When the architect connects two agents, the canvas redraws, and a refused edit shows what changed in between without losing what you typed.

Live updates

Over every API

Drafts, the graph, the playground, and architect prompts are reachable over REST, MCP, and all four SDKs, so you can script the whole studio flow.

Agentic apps

Apps with their own front door

An agentic app groups agents behind one entry agent and gives end users a chat UI at its own URL, separate from the operator console.

The app's edges are its delegation policy. Garrison computes each member's allow list and depth from the graph, writes them into member drafts, and reports drift instead of overwriting a deliberate manual edit.

An app revision pins every member's published revision, and app promotion moves every member to the next environment together, or nothing moves.

What end users get

  • The app's name, logo, colors, and welcome text, loaded at runtime, so branding changes need no rebuild.
  • Streaming answers that resume after a dropped connection.
  • A file panel with every file the agents wrote in the conversation, each version, and downloads, updating live.
  • Nine languages and light and dark themes.

Sign-in

  • AppUsers (default): tenant users who hold the AppUser role on the app.
  • TenantUsers: any active user of the tenant.
  • Anonymous: anyone with the URL, only when anonymousEnabled is also true.

App sessions (gas_ tokens) work only on that app's gateway, reach only their owner's conversations, expire after 480 minutes (60 for anonymous), and are rate limited. Thinking and tool calls stay hidden unless the app turns on operator detail.

Security

Multi-tenant from the first request

Every request, from a person, an application, an MCP client, an A2A agent, or a running agent, goes through the same identity and permission model.

Tenants and RBAC

Tenants, users, credentials, roles, permissions, and assignments scoped to a tenant or a single resource. Effective permissions can be inspected. A credential never gets more than its owning user, and cross-tenant reads return 404.

Authorization

Built-in roles

Roles such as Releaser for promotions and AppUser for app access ship ready to assign. Promotion to an environment needs Execute on Promotion for that environment.

Built-in roles

No default passwords

Docker Compose and the Kubernetes scripts generate keys and the administrator password. The server refuses to start with the public built-in defaults outside an explicit development mode.

Before you expose Garrison

Secrets stay secrets

Harness credentials are stored as encrypted tenant secrets under a versioned master key, never as worker environment variables, and are scrubbed from logs, run output, and transcripts.

Stored secrets · Key rotation

Isolation per run

The KubernetesJob executor runs each run in its own hardened pod with an egress allowlist. Deployments marked Untrusted require an isolating worker; the Process executor is for trusted work.

Harness isolation

Run tokens and approvals

Run tokens are short-lived and lease-fenced, and revoked when the run ends. Tool calls that need permission, and every studio apply, wait for a person in one approvals inbox. Every change is audited.

Approvals · Audit

Observability

Operations you can explain

Every run, studio and playground runs included, lands in the same history, transcripts, and telemetry.

Runs and run trees

Run trees show delegation and fan-out groups with their join policy and budget use. Queued runs carry a blocked reason, and placement explanations say why a run can or cannot be placed.

Analytics

The dashboard charts time to first token, queue and execution time, tokens, cost, outcomes, and tool calls by agent, harness, deployment, and model.

Metrics, traces, logs

Prometheus metrics, OpenTelemetry traces, logs, and Grafana dashboards connect the control plane to worker activity. Compose starts the observability stack by default.
