How it works

How Garrison works

Garrison accepts a request to run an agent over REST, MCP, A2A, or an app, turns it into a fully resolved command line, and hands it to a worker that pulls it. The studio and apps are built on that same path.

The parts

Control plane, workers, and database

The control plane (Command) runs as N replicas that share state through the database. Workers (Post) run as M replicas and only make outbound calls.

Architecture

A run

The life of a run

The control plane compiles each run into a fully resolved execution spec. The worker never reads the database and never renders a template.

  1. Invoke

    A caller invokes an agent over REST, MCP, A2A, or an app. Garrison checks Execute on the agent, picks a deployment by weight, validates overrides, and stores the run as Queued.

  2. Lease

    A worker's long poll claims the run with a compare-and-set update that bumps its fencing epoch. Delegated runs are claimed ahead of new top-level work.

  3. Compile

    Garrison mints a run token and compiles the ExecutionSpec: revision, assets, file space, command line, environment, files, stdin, parser, timeouts, and the MCP servers to check before launch.

  4. Execute

    The worker prepares the workspace and HOME, places assets, syncs files/, runs MCP pre-flight, launches the harness, and parses its output into events.

  5. Stream

    Events go back in batches, fenced by epoch, and callers follow them over SSE or WebSocket from any replica.

  6. Finalize

    The worker writes changed files back to the file space and completes the run. Garrison stores the result and revokes the run token.

When something fails

If a worker dies, its lease expires and the leader requeues or fails the run according to its effect policy. A stale worker that comes back is fenced out by its old epoch, so it cannot overwrite a result.

If a control-plane replica crashes, clients and workers retry against another one, and another replica takes over maintenance within the leader lease. On SIGTERM a replica drains: readiness answers 503, long polls return empty, and SSE streams close so clients reconnect elsewhere and resume.

Effect policies

AtMostOnce never retries a lost running attempt. AtLeastOnce permits retries and possible duplicate effects. Journaled resumes only when Garrison has safe checkpoint and effect evidence. Arbitrary shell commands and third-party MCP calls stay outside the journal.

Studio

From a draft to a live app

The architect is an ordinary hosted agent. Its runs call studio tools over Garrison MCP with a run token, the same way any orchestrator calls another agent.

  1. Edit the draft

    A person on the canvas and the architect in chat edit the same draft. Each change carries the version it read and is broadcast on the draft's channel.

  2. Request apply

    The studio validates the draft by manifest dry run and creates a DraftApply approval holding the diff.

  3. A person decides

    Someone with permission to apply manifests approves. If live configuration changed since validation, the draft is validated again first.

  4. Apply and deploy

    The bundle applies in one transaction, changed agents publish new revisions, and their dev deployments are repinned.

  5. Promote

    A releaser promotes the app to staging and prod; rollback restores every member's previous pin together.

Apps

How end users reach an app

The app gateway accepts only app session tokens, and the management API refuses them.

The app UI at /apps/{slug}/ loads the app's branding, starts a session, and talks only to /v1.0/apps/{slug}/.... A new conversation starts on the entry deployment of the app's live environment, with its own file space.

Runs started through an app run as the app, with the end user recorded as the caller. The entry agent's delegation policy, derived from the app's edges, bounds what the run may call.

Turns stream as server-sent events that resume after Last-Event-ID, and file changes arrive on their own stream so the file panel updates while agents work.
