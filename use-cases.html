Research overview

A research desk that hands back a PDF

The research-overview example is an app whose orchestrator fans out to researchers, has a writer put the report in the conversation file space, and has the doc-converter turn it into a PDF.

Builder Designing it in the studio

  1. Give the architect a deployment

    The builder creates a deployment of the seeded agent-architect on the harness and model they want, with the default architect prompt or the team's clone that adds their naming and citation conventions.

  2. Describe the app

    "I need an agent that researches a topic, collects sources in parallel, writes a report, and hands back a PDF." The architect writes four agents into a draft: an orchestrator, a researcher, a writer, and the doc-converter.

  3. Shape it on the canvas

    The canvas shows the orchestrator calling the researcher (parallel calls allowed), the writer, and the converter. The builder adjusts edges by mouse or keyboard, and the architect sees each change in its next turn.

  4. Add assets and capabilities

    The builder adds a reference document for report styles and a skill. The architect reads the capability catalog and picks the doc-converter agent as the conversion source.

  5. Set the runtime

    On the Runtime panel the builder sets the researcher's model and time limit per environment. Each edit becomes one draft change.

  6. Try it

    The builder runs the draft in the playground over two turns, checks the run tree and the files, and opens the compile preview to see the exact command line.

  7. Approve and deploy

    The architect requests apply. The builder reviews the diff and dry-run result and approves. Revisions publish and the app deploys to dev.

  8. Promote

    After testing in dev, a releaser promotes the whole app to staging and prod. When a later prompt change misbehaves, rolling back restores every member's previous revision together.

End user Using it

  1. Open the app

    The end user opens the app's URL and sees Research Desk with its welcome text. The example allows anonymous use; other apps ask for a sign-in.

  2. Ask

    "Give me an overview of decision models." The app gateway starts a conversation on the entry deployment of the live environment, with a new file space.

  3. Fan out

    The orchestrator checks the catalog, then fans out to researchers in one call. Each child writes its notes into the shared file space, and the file panel lists them as they appear.

  4. Gather

    The orchestrator gathers the results. If a researcher times out, gather still returns the others and the orchestrator reports partial coverage. With suspension enabled, its worker slot was free while it waited.

  5. Write

    The orchestrator asks the writer to draft report.md from the notes. A follow-up turn resumes the same harness session, and a rewrite becomes a new version with the old one kept in history.

  6. Convert

    The orchestrator calls the doc-converter, which runs pandoc and LibreOffice on a worker that advertises them. report.pdf appears in the file panel.

  7. Download

    The user downloads the PDF. The operator can open the same conversation in the dashboard: the transcript, the run tree with the fan-out group, and the same files.

Run it yourself. The bundle runs on the fake harness, with the orchestrator's tool calls scripted so the walkthrough repeats exactly. Apply it, open http://127.0.0.1:8080/apps/research-overview/, and ask for an overview. To run it for real, switch the deployments to a real harness and give each agent a system prompt; the architect can do that with you. The doc-converter needs a worker image built with --build-arg INCLUDE_DOC_TOOLS=true.
TOKEN=...   # a management token
B=http://127.0.0.1:8700/v1.0/api/tenants/default
curl -s -X POST "$B/manifests/apply" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/yaml" --data-binary @doc-converter/doc-converter.yaml
curl -s -X POST "$B/manifests/apply" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/yaml" --data-binary @research-overview/research-overview.yaml

Support triage

A support desk, built in the studio and exported

The support-triage example is a smaller app built in the studio and exported as a manifest bundle you can apply to any tenant.

A customer writes in. The entry agent, triage-desk, asks the classifier which queue the message belongs to (billing, outage, account, or other) and asks the knowledge lookup for the article that best answers it. Then it replies with both.

Both calls are one at a time, and the app's edges are the only calls the desk may make. The app is called Support Desk, greets people with "Tell us what went wrong.", and allows anonymous use in dev.

Why it is a good template

  • It shows the shape of most routing apps: one front agent, specialists behind it.
  • Every SDK's Agent Studio walkthrough applies it, opens a studio draft from it, and chats with it through the app gateway as an anonymous user.
  • It runs on the fake harness. Swap the harness profiles for a real harness and give the agents prompts to run it for real.

More ways teams use it

Other patterns

Coding agents behind an API

Give products and internal tools a Claude Code, Codex, opencode, or pi agent with workspaces, secrets, and limits set by the operator, not the caller.

Workflows with human review

Draft, review, and revise in pipeline stages, with a person approving between stages and risky tool calls held until someone decides.

Scheduled and event-driven agents

Nightly reports on a cron schedule, work that starts from a signed webhook, and a signed notification when it finishes.

A shared agent platform

One fleet of workers for many teams, each with its own agents, secrets, permissions, quotas, and run history.

Comparing harnesses and models

Two deployments of one agent on different harnesses or models, traffic split by weight, results compared on the Analytics page.

Document conversion as a capability

The doc-converter turns Markdown into Word or PDF with a reference document. The same job can come from another agent, an MCP tool, or a tool on the worker host.
